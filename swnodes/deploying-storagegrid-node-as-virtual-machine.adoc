= VMware vSphereを使用してStorageGRIDの仮想マシンとしてグリッドノードを導入
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
VMware vSphere Web Client を使用して、各グリッドノードを仮想マシンとしてデプロイします。デプロイ中に、各グリッドノードが作成され、1つ以上の StorageGRID ネットワークに接続されます。

StorageGRID アプライアンスストレージノードを導入する必要がある場合は、 https://docs.netapp.com/us-en/storagegrid-appliances/installconfig/deploying-appliance-storage-node.html["アプライアンスストレージノードをデプロイする"^]を参照してください。

必要に応じて、ノードの電源を入れる前に、ノードのポートを再マッピングしたり、CPUやメモリの設定を増やしたりすることができます。

.開始する前に
* link:index.html["設置の計画と準備"]の確認方法を確認し、ソフトウェア、CPU、RAM、ストレージ、パフォーマンスに関する要件を理解しています。
* VMware vSphere ハイパーバイザーに精通しており、この環境で仮想マシンをデプロイした経験があること。
+

NOTE:  `open-vm-tools`パッケージは、VMware Tools に似たオープンソースの実装であり、StorageGRID 仮想マシンに付属しています。VMware Tools を手動でインストールする必要はありません。

* VMware 用の正しいバージョンの StorageGRID インストールアーカイブをダウンロードして展開済みです。
+

CAUTION: 拡張または復旧操作の一環として新しいノードをデプロイする場合は、現在グリッドで実行されているバージョンの StorageGRID を使用する必要があります。

* StorageGRID Virtual Machine Disk (`.vmdk`） ファイル：


[listing, subs="specialcharacters,quotes"]
----
NetApp-_SG-version_-SHA.vmdk
----
* デプロイするグリッドノードの種類ごとに、 `.ovf`および `.mf`ファイルが必要です：
+
[cols="1a,1a"]
|===
| ファイル名 | 説明 


| vsphere-primary-admin.ovf vsphere-primary-admin.mf  a| 
プライマリ管理ノードのテンプレートファイルとマニフェストファイル。



| vsphere-non-primary-admin.ovf vsphere-non-primary-admin.mf  a| 
プライマリではない管理ノード用のテンプレートファイルとマニフェストファイル。



| vsphere-storage.ovf vsphere-storage.mf  a| 
ストレージノードのテンプレートファイルとマニフェストファイル。



| vsphere-gateway.ovf vsphere-gateway.mf  a| 
ゲートウェイノードのテンプレートファイルとマニフェストファイル。

|===
*  `.vdmk`、 `.ovf`、および `.mf`ファイルはすべて同じディレクトリにあります。
* 障害ドメインを最小限に抑えるための計画を立てています。たとえば、すべての Gateway Node を単一の vSphere ESXi ホストにデプロイしないようにしてください。
+

CAUTION: 本番環境への展開においては、1台の仮想マシン上で複数のストレージノードを実行しないでください。複数の仮想マシンを同じESXiホスト上で実行することで、許容できない障害ドメインの問題が発生する可能性がある場合は、実行しないでください。

* ノードを拡張または復旧操作の一部としてデプロイする場合は、link:../expand/index.html["StorageGRID システムを拡張するための手順"]またはlink:../maintain/index.html["復旧およびメンテナンス手順"]があります。
* StorageGRID ノードを NetApp ONTAP システムからストレージが割り当てられた仮想マシンとして導入する場合は、ボリュームに FabricPool 階層化ポリシーが有効になっていないことを確認してください。たとえば、StorageGRID ノードが VMware ホスト上の仮想マシンとして実行されている場合は、ノードのデータストアを支えるボリュームに FabricPool 階層化ポリシーが有効になっていないことを確認してください。StorageGRID ノードで使用するボリュームの FabricPool 階層化を無効にすることで、トラブルシューティングとストレージ操作が簡素化されます。
+

NOTE: FabricPoolを使用してStorageGRIDに関連するデータをStorageGRID自体に階層化することは絶対にしないでください。StorageGRIDにStorageGRIDデータを階層化すると、トラブルシューティングと運用がより複雑になります。



.タスク概要
VMwareノードを最初にデプロイする場合、拡張時に新しいVMwareノードを追加する場合、または復旧操作の一環としてVMwareノードを交換する場合は、以下の手順に従ってください。手順に記載されている場合を除き、ノードのデプロイ手順は、管理ノード、ストレージノード、ゲートウェイノードを含むすべてのノードタイプで同じです。

新しい StorageGRID システムをインストールする場合：

* ノードは任意の順序でデプロイできます。
* 各仮想マシンがグリッドネットワーク経由でプライマリ管理ノードに接続できることを確認する必要があります。
* グリッドを構成する前に、すべてのグリッドノードをデプロイする必要があります。


拡張または復旧操作を実行する場合：

* 新しい仮想マシンがグリッドネットワーク上の他のすべてのノードに接続できることを確認する必要があります。


ノードのポートを再マッピングする必要がある場合は、ポートの再マッピング設定が完了するまで、新しいノードの電源をオンにしないでください。


NOTE: ポート再マッピングのサポートは非推奨となり、今後のリリースで削除されます。再マッピングされたポートを削除するには、link:../maintain/removing-port-remaps-on-bare-metal-hosts.html["ベアメタルホスト上のポートリマップを削除する"]を参照してください。

.手順
. vCenterを使用して、OVFテンプレートをデプロイします。
+
URLを指定する場合は、以下のファイルを含むフォルダを指定してください。それ以外の場合は、ローカルディレクトリからこれらのファイルをそれぞれ選択してください。

+
[listing, subs="specialcharacters,quotes"]
----
NetApp-_SG-version_-SHA.vmdk
vsphere-_node_.ovf
vsphere-_node_.mf
----
+
例えば、これが最初にデプロイするノードである場合は、これらのファイルを使用して StorageGRID システムのプライマリ管理ノードをデプロイします：

+
[listing, subs="specialcharacters,quotes"]
----
NetApp-_SG-version_-SHA.vmdk
vsphere-primary-admin.ovf
vsphere-primary-admin.mf
----
. 仮想マシンに名前を付けてください。
+
標準的な慣例として、仮想マシンとグリッドノードの両方に同じ名前を使用します。

. 仮想マシンを適切な vApp またはリソース プールに配置します。
. プライマリ管理ノードをデプロイする場合は、エンドユーザー使用許諾契約書を読んで同意してください。
+
お使いの vCenter のバージョンによっては、エンドユーザーライセンス契約への同意、仮想マシン名の指定、データストアの選択といった手順の順序が異なります。

. 仮想マシンのストレージを選択します。
+
復旧操作の一環としてノードをデプロイする場合は、<<step_recovery_storage,ストレージ復旧手順>>の手順に従って、新しい仮想ディスクの追加、障害が発生したグリッドノードからの仮想ハードディスクの再接続、またはその両方を実行してください。

+
ストレージノードをデプロイする際は、3つ以上のストレージボリュームを使用し、各ストレージボリュームの容量は4 TB以上にしてください。ボリューム0には少なくとも4 TBを割り当てる必要があります。

+

NOTE: ストレージノードの .ovf ファイルは、ストレージ用の複数の VMDK を定義します。これらの VMDK がストレージ要件を満たさない場合は、ノードの電源を入れる前に、それらを削除し、適切な VMDK または RDM をストレージとして割り当てる必要があります。VMDK は VMware 環境でより一般的に使用されており管理が容易ですが、RDM はより大きなオブジェクトサイズ（例：100 MB 以上）を使用するワークロードに対して、より優れたパフォーマンスを提供する場合があります。

+

NOTE: StorageGRID のインストールによっては、一般的な仮想化ワークロードよりも大容量でアクティブなストレージボリュームを使用する場合があります。最適なパフォーマンスを実現するために、 `MaxAddressableSpaceTB`などのハイパーバイザーパラメーターを調整する必要がある場合があります。パフォーマンスが低下した場合は、仮想化サポート担当者に連絡して、ワークロード固有の構成チューニングによって環境が改善されるかどうかを確認してください。

. ネットワークを選択します。
+
各送信元ネットワークに対して宛先ネットワークを選択することで、ノードが使用する StorageGRID ネットワークを決定します。

+
** グリッドネットワークが必要です。vSphere環境で宛先ネットワークを選択する必要があります。+ グリッドネットワークは、StorageGRID の内部トラフィックすべてに使用されます。グリッド内のすべてのノード間、すべてのサイトおよびサブネット間で接続性を提供します。グリッドネットワーク上のすべてのノードは、他のすべてのノードと通信できる必要があります。
** 管理ネットワークを使用する場合は、vSphere環境で別の宛先ネットワークを選択してください。管理ネットワークを使用しない場合は、グリッドネットワークで選択したのと同じ宛先を選択してください。
** クライアントネットワークを使用する場合は、vSphere環境で別の宛先ネットワークを選択してください。クライアントネットワークを使用しない場合は、グリッドネットワークで選択したのと同じ宛先を選択してください。
** 管理者ネットワークまたはクライアントネットワークを使用する場合、ノードは同じ管理者ネットワークまたはクライアントネットワーク上にある必要はありません。


. 「テンプレートのカスタマイズ」では、必要な StorageGRID ノードのプロパティを設定します。
+
.. ノード名を入力してください。
+

NOTE: グリッドノードを復旧する場合は、復旧するノードの名前を入力する必要があります。

.. 「一時インストールパスワード」ドロップダウンを使用して一時インストールパスワードを指定すると、新しいノードがグリッドに参加する前に、VM コンソールまたは StorageGRID インストール API にアクセスするか、SSH を使用することができます。
+

NOTE: 一時的なインストールパスワードは、ノードのインストール時のみ使用されます。ノードがグリッドに追加されたあとは、link:../admin/change-node-console-password.html["ノードコンソールのパスワード"]を使用してアクセスできます。これはリカバリパッケージ内の `Passwords.txt`ファイルに記載されています。

+
*** *ノード名を使用*：*ノード名*フィールドに入力した値が、一時的なインストールパスワードとして使用されます。
*** *カスタムパスワードを使用する*：カスタムパスワードは、一時的なインストールパスワードとして使用されます。
*** *パスワードを無効にする*：一時的なインストールパスワードは使用されません。インストールの問題をデバッグするために VM にアクセスする必要がある場合は、link:troubleshooting-installation-issues.html["インストールに関する問題のトラブルシューティング"]を参照してください。


.. 「カスタムパスワードを使用する」を選択した場合は、「カスタムパスワード」フィールドに、使用する一時的なインストールパスワードを指定してください。
.. 「グリッドネットワーク（eth0）」セクションで、「グリッドネットワークIP構成」に対して「STATIC」または「DHCP」を選択します。
+
*** STATICを選択した場合は、*グリッドネットワークIP*、*グリッドネットワークマスク*、*グリッドネットワークゲートウェイ*、および*グリッドネットワークMTU*を入力してください。
*** DHCPを選択した場合、*グリッドネットワークIP*、*グリッドネットワークマスク*、および*グリッドネットワークゲートウェイ*が自動的に割り当てられます。


.. *Primary Admin IP* フィールドに、グリッドネットワークのプライマリ管理ノードの IP アドレスを入力します。
+

NOTE: デプロイするノードがプライマリ管理ノードである場合は、この手順は適用されません。

+
プライマリ管理ノードのIPアドレスを省略した場合、プライマリ管理ノード、またはADMIN_IPが設定された他のグリッドノードが少なくとも1つ同じサブネット上に存在する場合、IPアドレスは自動的に検出されます。ただし、ここではプライマリ管理ノードのIPアドレスを設定することをお勧めします。

.. 「管理ネットワーク（eth1）」セクションで、「管理ネットワークのIP設定」に対して STATIC、DHCP、または DISABLED を選択します。
+
*** 管理ネットワークを使用しない場合は、DISABLED を選択し、管理ネットワークの IP アドレスに *0.0.0.0* と入力してください。その他の項目は空欄のままで構いません。
*** 「STATIC」を選択した場合は、*管理ネットワークIP*、*管理ネットワークマスク*、*管理ネットワークゲートウェイ*、および*管理ネットワークMTU*を入力してください。
*** 「STATIC」を選択した場合は、*管理者ネットワークの外部サブネットリスト*を入力してください。ゲートウェイも設定する必要があります。
*** DHCPを選択した場合、*管理ネットワークIP*、*管理ネットワークマスク*、および*管理ネットワークゲートウェイ*が自動的に割り当てられます。


.. *クライアントネットワーク（eth2）*セクションで、*クライアントネットワークIP構成*に対して「STATIC」、「DHCP」、または「DISABLED」を選択します。
+
*** クライアントネットワークを使用しない場合は、DISABLED を選択し、クライアントネットワーク IP に *0.0.0.0* と入力してください。その他のフィールドは空白のままにしておくことができます。
*** 「STATIC」を選択した場合は、*クライアントネットワークIP*、*クライアントネットワークマスク*、*クライアントネットワークゲートウェイ*、および*クライアントネットワークMTU*を入力してください。
*** DHCPを選択した場合、*クライアントネットワークIP*、*クライアントネットワークマスク*、および*クライアントネットワークゲートウェイ*が自動的に割り当てられます。




. 仮想マシンの構成を確認し、必要に応じて変更を加えてください。
. 準備が整ったら、*Finish* を選択して仮想マシンのアップロードを開始してください。
. [[step_recovery_storage]]このノードをリカバリ操作の一部としてデプロイし、これがフルノードリカバリでない場合は、デプロイ完了後に以下の手順を実行してください：
+
.. 仮想マシンを右クリックし、「設定の編集」を選択します。
.. ストレージ用に指定されている各デフォルト仮想ハードディスクを選択し、*削除*を選択します。
.. データ復旧の状況に応じて、ストレージ要件に合わせて新しい仮想ディスクを追加したり、以前に削除された障害グリッドノードから保存された仮想ハードディスクを再接続したり、あるいはその両方を行ってください。
+
以下の重要なガイドラインにご注意ください：

+
*** 新しいディスクを追加する場合は、ノード復旧前に使用されていたものと同じ種類のストレージデバイスを使用する必要があります。
*** ストレージノードの .ovf ファイルは、ストレージ用の複数の VMDK を定義します。これらの VMDK がストレージ要件を満たさない場合は、ノードの電源を入れる前に、それらを削除し、適切な VMDK または RDM をストレージとして割り当てる必要があります。VMDK は VMware 環境でより一般的に使用されており管理が容易ですが、RDM はより大きなオブジェクトサイズ（例：100 MB 以上）を使用するワークロードに対して、より優れたパフォーマンスを提供する場合があります。




. [[vmware-remap-ports]]このノードで使用されているポートを再マッピングする必要がある場合は、次の手順に従ってください。
+
エンタープライズネットワークポリシーによって、StorageGRID が使用する1つ以上のポートへのアクセスが制限されている場合は、ポートを再マッピングする必要があります。StorageGRID が使用するポートについては、link:../network/index.html["ネットワーク構築ガイドライン"]を参照してください。

+

NOTE: ロードバランサーのエンドポイントで使用されているポートを再マッピングしないでください。

+
.. 新しい仮想マシンを選択します。
.. 「設定」タブから、*設定* > *vApp オプション*を選択します。*vApp オプション*の場所は、vCenterのバージョンによって異なります。
.. *Properties* テーブルで、PORT_REMAP_INBOUND と PORT_REMAP を見つけます。
.. ポートの受信通信と送信通信の両方を対称的にマッピングするには、*PORT_REMAP* を選択します。
+

NOTE: ポート再マッピングのサポートは非推奨となり、今後のリリースで削除されます。再マッピングされたポートを削除するには、link:../maintain/removing-port-remaps-on-bare-metal-hosts.html["ベアメタルホスト上のポートリマップを削除する"]を参照してください。

+

NOTE: PORT_REMAPのみが設定されている場合、指定したマッピングは受信通信と送信通信の両方に適用されます。PORT_REMAP_INBOUNDも指定されている場合、PORT_REMAPは送信通信にのみ適用されます。

+
... 「値の設定」を選択します。
... ポートマッピングを入力してください：
+
`<network type>/<protocol>/<default port used by grid node>/<new port>`

+
`<network type>` は grid、admin、または client であり、 `<protocol>` は tcp または udp です。

+
例えば、SSHトラフィックをポート22からポート3022に再マッピングするには、次のように入力します：

+
`client/tcp/22/3022`

+
カンマ区切りのリストを使用して、複数のポートを再マッピングできます。

+
次に例を示します。

+
`client/tcp/18082/443, client/tcp/18083/80`

... 「OK」を選択します。


.. ノードへの受信通信に使用するポートを指定するには、*PORT_REMAP_INBOUND* を選択します。
+

NOTE: PORT_REMAP_INBOUNDを指定し、PORT_REMAPの値を指定しない場合、そのポートの送信通信は変更されません。

+
... 「値の設定」を選択します。
... ポートマッピングを入力してください：
+
`<network type>/<protocol>/<remapped inbound port>/<default inbound port used by grid node>`

+
`<network type>` は grid、admin、または client であり、 `<protocol>` は tcp または udp です。

+
例えば、ポート3022に送信される受信SSHトラフィックをグリッドノードのポート22で受信するように再マッピングするには、次のように入力します：

+
`client/tcp/3022/22`

+
カンマ区切りのリストを使用して、複数の受信ポートを再マッピングできます。

+
次に例を示します。

+
`grid/tcp/3022/22, admin/tcp/3022/22`

... 「OK」を選択します。




. ノードの CPU またはメモリをデフォルト設定から増やす場合は、次の手順に従ってください。
+
.. 仮想マシンを右クリックし、「設定の編集」を選択します。
.. 必要に応じてCPUの数やメモリ容量を変更してください。
+
*Memory Reservation* を、仮想マシンに割り当てられた *Memory* と同じサイズに設定してください。

.. 「OK」を選択します。


. 仮想マシンの電源をオンにします。


.終了後の操作
このノードを拡張または復旧手順の一環としてデプロイした場合は、該当する手順に戻って手順を完了してください。
