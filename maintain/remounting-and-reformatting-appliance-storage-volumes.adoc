= StorageGRIDアプライアンスストレージボリュームの再マウントと再フォーマット（手動手順）
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
保存されたストレージボリュームを再マウントし、障害が発生したストレージボリュームを再フォーマットするには、2つのスクリプトを手動で実行する必要があります。最初のスクリプトは、StorageGRID ストレージボリュームとして適切にフォーマットされたボリュームを再マウントします。2番目のスクリプトは、マウントされていないボリュームを再フォーマットし、必要に応じてCassandraデータベースを再構築して、サービスを開始します。

.開始する前に
* 交換が必要であると判明している故障したストレージボリュームのハードウェアは、既に交換済みです。
+
 `sn-remount-volumes`スクリプトを実行すると、障害が発生した他のストレージボリュームを特定するのに役立つ場合があります。

* ストレージノードの廃止処理が進行中ではないことを確認したか、またはノードの廃止処理を一時停止しました。（グリッドマネージャーで、*Maintenance* > *Tasks* > *Decommission* を選択します。）
* 拡張処理が進行中ではないことを確認しました。（グリッドマネージャで、「メンテナンス」＞「タスク」＞「拡張」を選択します。）



CAUTION: 複数のストレージノードがオフラインになっている場合は、テクニカルサポートにお問い合わせください。 `sn-recovery-postinstall.sh`スクリプトは実行しないでください。

.タスク概要
この手順を完了するには、以下の概要タスクを実行します：

* 復旧したストレージノードにログインします。
*  `sn-remount-volumes`スクリプトを実行して、適切にフォーマットされたストレージボリュームを再マウントします。このスクリプトを実行すると、以下の処理が行われます：
+
** 各ストレージボリュームをマウントおよびアンマウントして、XFSジャーナルを再生します。
** XFSファイルの整合性チェックを実行します。
** ファイルシステムが一貫している場合、ストレージボリュームが適切にフォーマットされた StorageGRID ストレージボリュームであるかどうかを判断します。
** ストレージボリュームが正しくフォーマットされている場合、ストレージボリュームを再マウントします。当該ボリュームに関する既存のデータはすべてそのまま保持されます。


* スクリプトの出力結果を確認し、問題があれば解決してください。
*  `sn-recovery-postinstall.sh`スクリプトを実行します。このスクリプトを実行すると、以下の処理が行われます。
+

CAUTION: 障害が発生したストレージボリュームの再フォーマットとオブジェクトメタデータの復元のために `sn-recovery-postinstall.sh`（ステップ4）を実行する前に、リカバリ中のストレージノードを再起動しないでください。 `sn-recovery-postinstall.sh`が完了する前にストレージノードを再起動すると、起動しようとするサービスでエラーが発生し、StorageGRIDアプライアンスノードがメンテナンスモードを終了します。

+
**  `sn-remount-volumes`スクリプトがマウントできなかったか、フォーマットが不適切であることが判明したストレージボリュームを再フォーマットします。
+

NOTE: ストレージボリュームが再フォーマットされると、そのボリューム上のデータはすべて失われます。ILMルールが複数のオブジェクトコピーを保存するように構成されている場合、グリッド内の他の場所からオブジェクトデータを復元するには、追加の手順を実行する必要があります。

** 必要に応じて、ノード上のCassandraデータベースを再構築します。
** ストレージノード上でサービスを開始します。




.手順
. 復旧したストレージノードにログインします。
+
.. 次のコマンドを入力します： `ssh admin@_grid_node_IP_`
..  `Passwords.txt`ファイルに記載されているパスワードを入力してください。
.. 以下のコマンドを入力して root に切り替えます： `su -`
..  `Passwords.txt`ファイルに記載されているパスワードを入力してください。


+
rootとしてログインすると、プロンプトが `$`から `#`に変わります。

. 最初のスクリプトを実行して、適切にフォーマットされたストレージボリュームを再マウントします。
+

NOTE: すべてのストレージボリュームが新規でフォーマットが必要な場合、またはすべてのストレージボリュームが故障している場合は、この手順をスキップして、2番目のスクリプトを実行し、マウントされていないすべてのストレージボリュームを再フォーマットできます。

+
.. スクリプトを実行します： `sn-remount-volumes`
+
データを含むストレージボリュームでこのスクリプトを実行するには、数時間かかる場合があります。

.. スクリプトの実行中は、出力結果を確認し、表示されるプロンプトに回答してください。
+

NOTE: 必要に応じて、 `tail -f`コマンドを使用して、スクリプトのログファイルの内容を監視できます（(`/var/local/log/sn-remount-volumes.log`）。ログファイルには、コマンドライン出力よりも詳細な情報が含まれています。

+
出力例では、1つのストレージボリュームが正常に再マウントされ、3つのストレージボリュームでエラーが発生しました。

+
*** `/dev/sdb` は、XFSファイルシステムの整合性チェックに合格し、有効なボリューム構造を持っていたため、正常に再マウントされました。スクリプトによって再マウントされたデバイス上のデータは保持されます。
*** `/dev/sdc`ストレージボリュームが新規であるか破損しているため、XFSファイルシステムの整合性チェックに失敗しました。
*** `/dev/sdd`ディスクが初期化されていないか、ディスクのスーパーブロックが破損しているため、マウントできませんでした。スクリプトがストレージボリュームをマウントできない場合、ファイルシステムの整合性チェックを実行するかどうかを確認するメッセージが表示されます。
+
**** ストレージボリュームが新しいディスクに接続されている場合は、プロンプトに対して *N* と回答してください。新しいディスクのファイルシステムを確認する必要はありません。
**** ストレージボリュームが既存のディスクに接続されている場合は、プロンプトに対して *Y* と答えてください。ファイルシステムチェックの結果を利用して、破損の原因を特定できます。結果は `/var/local/log/sn-remount-volumes.log`ログファイルに保存されます。


*** `/dev/sde`はXFSファイルシステムの整合性チェックに合格し、有効なボリューム構造を持っていましたが、 `volID`ファイル内のLDRノードIDがこのストレージノードのID（上部に表示される `configured LDR noid`）と一致しませんでした。このメッセージは、このボリュームが別のストレージノードに属していることを示しています。




. スクリプトの出力結果を確認し、問題があれば解決してください。
+

CAUTION: ストレージボリュームがXFSファイルシステムの整合性チェックに失敗した場合、またはマウントできなかった場合は、出力されたエラーメッセージを注意深く確認してください。これらのボリュームに対して `sn-recovery-postinstall.sh`スクリプトを実行することの意味を理解する必要があります。

+
.. 結果に、想定していたすべてのボリュームのエントリが含まれていることを確認してください。リストに載っていないボリュームがある場合は、スクリプトを再実行してください。
.. マウントされているすべてのデバイスのメッセージを確認してください。ストレージボリュームがこのストレージノードに属していないことを示すエラーがないことを確認してください。
+
この例では、/dev/sde の出力に次のエラーメッセージが含まれています：

+
[listing]
----
Error: This volume does not belong to this node. Fix the attached volume and re-run this script.
----
+

CAUTION: ストレージボリュームが別のストレージノードに属していると報告された場合は、テクニカルサポートにお問い合わせください。 `sn-recovery-postinstall.sh`スクリプトを実行すると、ストレージボリュームが再フォーマットされ、データ損失が発生する可能性があります。

.. ストレージデバイスをマウントできなかった場合は、デバイス名をメモし、デバイスを修理または交換してください。
+

NOTE: マウントできなかったストレージデバイスは、修理または交換する必要があります。

+
デバイス名を使用してボリューム ID を検索します。これは、オブジェクトデータをボリュームに復元するための `repair-data`スクリプトを実行する際に必要な入力です（次の手順）。

.. マウントできないデバイスをすべて修理または交換した後、 `sn-remount-volumes`スクリプトを再度実行して、再マウント可能なすべてのストレージボリュームが再マウントされたことを確認します。
+

CAUTION: ストレージボリュームをマウントできない場合、またはフォーマットが正しくない場合に、次の手順に進むと、そのボリュームおよびボリューム上のすべてのデータが削除されます。オブジェクトデータのコピーが2つあった場合、次の手順（オブジェクトデータの復元）が完了するまでは、コピーは1つだけになります。



+

CAUTION: 障害が発生したストレージボリュームに残っているデータがグリッド内の他の場所から再構築できないと思われる場合（たとえば、ILM ポリシーで 1 つのコピーのみを作成するルールを使用している場合、またはボリュームが複数のノードで障害を起こしている場合）は、 `sn-recovery-postinstall.sh`スクリプトを実行しないでください。代わりに、テクニカルサポートに連絡して、データの復旧方法を確認してください。

.  `sn-recovery-postinstall.sh`スクリプトを実行します： `sn-recovery-postinstall.sh`
+
このスクリプトは、マウントできなかったストレージボリューム、またはフォーマットが正しくないと判断されたストレージボリュームを再フォーマットし、必要に応じてノード上のCassandraデータベースを再構築し、ストレージノード上のサービスを開始します。

+
以下の点にご注意ください。

+
** スクリプトの実行には数時間かかる可能性があります。
** 一般的に、スクリプトの実行中はSSHセッションをそのままにしておく必要があります。
** SSHセッションがアクティブな間は、*Ctrl+C*を押さないでください。
** ネットワーク障害が発生した場合、スクリプトはバックグラウンドで実行され、SSHセッションを終了しますが、復旧ページから進行状況を確認できます。
** ストレージノードがRSMサービスを使用している場合、ノードサービスの再起動に伴い、スクリプトが5分間停止したように見えることがあります。RSMサービスが初めて起動する際には、この5分間の遅延が想定されます。
+

NOTE: RSMサービスは、ADCサービスを含むストレージノードに存在します。



+

NOTE: いくつかのStorageGRID復旧手順では、Reaperを使用してCassandraの修復処理を行います。関連するサービスまたは必要なサービスが開始されるとすぐに、修復は自動的に行われます。スクリプトの出力に「reaper」または「Cassandra repair」という記述が見られる場合があります。修復が失敗したことを示すエラーメッセージが表示された場合は、エラーメッセージに示されているコマンドを実行してください。

.  `sn-recovery-postinstall.sh`スクリプトの実行中は、Grid Managerのリカバリページを監視してください。
+
リカバリページの進行状況バーとステージ列には、 `sn-recovery-postinstall.sh`スクリプトの概要ステータスが表示されます。

+
image:recovering_cassandra.png["Grid Management Interfaceで復旧の進捗状況を示すスクリーンショット"]

.  `sn-recovery-postinstall.sh`スクリプトがノード上でサービスを開始した後、スクリプトによってフォーマットされたストレージボリュームにオブジェクトデータを復元できます。
+
スクリプトは、Grid Manager のボリューム復元プロセスを使用するかどうかを確認します。

+
** ほとんどの場合、link:../maintain/restoring-volume.html["Grid Managerを使用してオブジェクトデータを復元する"]。回答 `y` Grid Manager を使用します。
** まれなケースとして、技術サポートから指示された場合、または交換ノードのオブジェクトストレージに使用できるボリュームが元のノードよりも少ないことがわかっている場合は、link:restoring-object-data-to-storage-volume-for-appliance.html["オブジェクトデータを手動で復元する"] `repair-data`スクリプトを使用する必要があります。これらのケースのいずれかに該当する場合は、 `n`と回答してください。
+
[NOTE]
====
Grid Manager のボリューム復元プロセス（オブジェクトデータを手動で復元する）の使用に `n`と回答した場合：

*** Grid Manager を使用してオブジェクトデータを復元することはできません。
*** Grid Manager を使用すると、手動復元作業の進捗状況を監視できます。


====
+
選択が完了すると、スクリプトが完了し、オブジェクトデータを復元するための次の手順が表示されます。これらの手順を確認したら、いずれかのキーを押してコマンドラインに戻ってください。
