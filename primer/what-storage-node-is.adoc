= StorageGRIDストレージ ノードとは何ですか？
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
ストレージノードは、オブジェクトデータとメタデータを管理および保存します。ストレージノードには、オブジェクトデータとメタデータをディスクに保存、移動、検証、取得するために必要なサービスとプロセスが含まれます。

StorageGRIDシステムの各サイトには、少なくとも3つのStorage Nodeが必要です。



[[types-of-storage-nodes]]
== ストレージノードの種類

インストール時に、インストールするストレージノードの種類を選択できます。これらのタイプは、ソフトウェアベースのストレージノードと、この機能をサポートするアプライアンスベースのストレージノードで利用可能です。

* データとメタデータを統合したストレージノード
* メタデータ専用ストレージノード
* データ専用ストレージノード


ストレージノードの種類は、次のような場合に選択できます。

* ストレージノードを最初にインストールする場合
* StorageGRID システム拡張時にストレージノードを追加する場合




[[data-and-metadata-storage-node-combined]]
=== データおよびメタデータ保存ノード（統合型）

デフォルトでは、すべての新しいストレージノードはオブジェクトデータとメタデータの両方を保存します。このタイプのストレージノードは、_複合_ストレージノードと呼ばれます。



[[metadata-only-storage-node]]
=== メタデータ専用ストレージノード

グリッドに非常に多くの小さなオブジェクトが格納されている場合、メタデータ専用のストレージノードを使用することは理にかなっている可能性があります。専用のメタデータ容量を導入することで、非常に多数の小さなオブジェクトに必要な容量と、それらのオブジェクトのメタデータに必要な容量とのバランスをより良く取ることができます。さらに、ハイパフォーマンスアプライアンスでホストされているメタデータ専用のストレージノードは、パフォーマンスを向上させることができます。

メタデータ専用ストレージノードには、特定のハードウェア要件があります。

* StorageGRID アプライアンスを使用する場合、メタデータ専用ノードは、1.9 TB ドライブを 12 台または 3.8 TB ドライブを 12 台搭載した SGF6112 アプライアンスでのみ構成できます。
* ソフトウェアベースのノードを使用する場合、メタデータのみのノードリソースは、既存のストレージノードのリソースと一致している必要があります。例えば：
+
** 既存の StorageGRID サイトで SG6000 または SG6100 アプライアンスを使用している場合、ソフトウェアベースのメタデータ専用ノードは以下の最小要件を満たす必要があります：
+
*** 128GBのRAM
*** 8コアCPU
*** Cassandraデータベース用に8 TB SSDまたは同等のストレージ（rangedb/0）


** 既存の StorageGRID サイトで 24 GB RAM、8 コア CPU、3 TB または 4 TB のメタデータストレージを備えた仮想ストレージノードを使用している場合、ソフトウェアベースのメタデータ専用ノードも同様のリソース（24 GB RAM、8 コア CPU、4 TB のメタデータストレージ（rangedb/0））を使用する必要があります。


* 新しい StorageGRID サイトを追加する場合、新しいサイトの総メタデータ容量は、少なくとも既存のサイトと同等である必要があります。新規サイトのリソースは、既存サイトのストレージノードのリソースと一致させる必要があります。



NOTE: メタデータのみのストレージノードには<<ldr-service,LDR service（RSMサービス）>>が含まれており、S3クライアントリクエストを処理できますが、StorageGRIDのパフォーマンスが向上しない可能性があります。



[[data-only-storage-node]]
=== データ専用ストレージノード

ストレージノードのパフォーマンス特性が異なる場合、データ専用のストレージノードを使用することは理にかなっている場合があります。たとえば、パフォーマンスを向上させるために、データのみの大容量スピニングディスクストレージノードと、メタデータのみのハイパフォーマンスストレージノードを組み合わせることができます。

さらに、CassandraからRAM容量の少ないノードを削除することで、メタデータ容量を増やすことができます。これにより、ノードごとのメタデータ容量の上限が引き上げられます。link:../admin/managing-object-metadata-storage.html["オブジェクトメタデータストレージの管理"]を参照してください。

<<adc-service,ADC service（RSMサービス）>>を含まないストレージノードを、データ専用のストレージノードに変換できます。link:../maintain/convert-to-data-only-node.html["ストレージノードをデータ専用ノードに変換する"]を参照してください。



[[required-storage-nodes-per-grid-and-per-site]]
== グリッドごと、サイトごとに必要なストレージノード数

トポロジで使用するストレージノードを選択する際には、グリッドまたはグリッド内の各サイトに以下の要素が含まれている必要があることに留意してください。

* サイトごと（単一サイトまたは複数サイトのグリッド内）：3<<adc-service,ADC>>ストレージノード（複合ストレージノードとメタデータ専用ストレージノードの任意の組み合わせが可能）
* シングルサイトグリッド：少なくとも2つのオブジェクトストレージノード（複合型とデータ専用型の任意の組み合わせが可能）
* マルチサイトグリッド：サイトごとに少なくとも1つのオブジェクトストレージノードが必要（複合型またはデータ専用型どちらでも可）




[[primary-services-for-storage-nodes]]
== ストレージノードの主要サービス

以下の表は、ストレージノードの主要サービスを示していますが、すべてのノードサービスが網羅されているわけではありません。


NOTE: ADCサービスやRSMサービスなど、一部のサービスは、通常、各サイトの3つのストレージノードにのみ存在します。

[cols="1a,3a"]
|===
| サービス | 主要機能 


 a| 
アカウント（acct）
 a| 
テナントのアカウントを管理します。

データ専用ストレージノードでは、このサービスは提供されません。



 a| 
[[adc-service]]管理ドメインコントローラー（ADC）
 a| 
トポロジーとグリッド全体の構成を維持します。

データ専用ストレージノードでは、このサービスは提供されません。

.詳細
[%collapsible]
====
管理ドメインコントローラー（ADC）サービスは、グリッドノードとそれらの間の接続を認証します。ADCサービスは、サイト内の最低3台のストレージノード上でホストされます。

ADCサービスは、サービスの場所や可用性を含むトポロジー情報を維持します。グリッドノードが他のグリッドノードから情報が必要な場合、または他のグリッドノードに何らかのアクションを実行させる必要がある場合、ADCサービスに連絡して、要求を処理するのに最適なグリッドノードを検索します。さらに、ADCサービスはStorageGRIDデプロイメントの構成バンドルのコピーを保持しており、どのグリッドノードでも現在の構成情報を取得できます。

分散およびアイランド運用を容易にするため、各 ADC サービスは、証明書、構成バンドル、およびサービスとトポロジに関する情報を、StorageGRID システム内の他の ADC サービスと同期します。

一般的に、すべてのグリッドノードは少なくとも1つのADCサービスへの接続を維持しています。これにより、グリッドノードは常に最新の情報にアクセスできるようになります。グリッドノードが接続すると、他のグリッドノードの証明書をキャッシュするため、ADCサービスが利用できない場合でも、既知のグリッドノードとの連携によりシステムが動作し続けることができます。新しいグリッドノードは、ADCサービスを使用することによってのみ接続を確立できます。

各グリッドノードの接続により、ADCサービスはトポロジー情報を収集できます。このグリッドノード情報には、CPU負荷、利用可能なディスク容量（ストレージがある場合）、サポートされているサービス、およびグリッドノードのサイトIDが含まれます。他のサービスは、トポロジークエリを通じてADCサービスにトポロジー情報を要求します。ADCサービスは、各クエリに対して、StorageGRIDシステムから受信した最新の情報で応答します。

Cassandra

データ専用ストレージノードでは、このサービスは提供されません。



 a| 
Cassandra Reaper

オブジェクトのメタデータの自動修復を実行します。

データ専用ストレージノードでは、このサービスは提供されません。

チャンク

分散データストア（DDS）
 a| 
オブジェクトのメタデータの保存状況を監視します。

.詳細
[%collapsible]
====
各ストレージノードには、分散データストア（DDS）サービスが含まれています。このサービスは Cassandra データベースと連携し、StorageGRID システムに格納されたオブジェクトメタデータに対してバックグラウンドタスクを実行します。

DDS サービスは、StorageGRID システムに取り込まれたオブジェクトの総数、およびシステムがサポートする各インターフェース（S3）を通じて取り込まれたオブジェクトの総数を追跡します。

 a| 
識別情報（idnt）
 a| 
LDAPとActive DirectoryからユーザーIDを統合します。

データ専用ストレージノードでは、このサービスは提供されません。



 a| 
[[ldr-service]]ローカルディストリビューションルーター（LDR）
 a| 
オブジェクト ストレージ プロトコルのリクエストを処理し、ディスク上のオブジェクトデータを管理します。

.詳細
[%collapsible]
====
_複合_ストレージノード、_データ専用_ストレージノード、および_メタデータ専用_ストレージノードのそれぞれには、ローカルディストリビューションルーター（LDR）サービスが含まれています。このサービスは、データストレージ、ルーティング、リクエスト処理など、コンテンツ転送機能を担います。LDRサービスは、データ転送負荷とデータトラフィック機能を処理することで、StorageGRIDシステムの中核的な役割を果たします。

LDRサービスは以下のタスクを処理します：

* クエリ
* 情報ライフサイクル管理（ILM）アクティビティ
* オブジェクト削除
* オブジェクトデータストレージ
* 別のLDRサービス（ストレージノード）からのオブジェクトデータ転送
* データストレージ管理
* S3プロトコルインターフェース


LDRサービスは、各S3オブジェクトを固有のUUIDにマッピングします。

オブジェクトストア:: LDRサービスの基盤となるデータストレージは、固定数のオブジェクトストア（ストレージボリュームとも呼ばれる）に分割されます。各オブジェクトストアは、それぞれ独立したマウントポイントです。
+
--
ストレージノード内のオブジェクトストアは、ボリュームIDと呼ばれる0000から002Fまでの16進数で識別されます。最初のオブジェクトストア（ボリューム0）には、Cassandraデータベースのオブジェクトメタデータ用の領域が確保されており、そのボリューム上の残りの領域はオブジェクトデータに使用されます。その他のオブジェクトストアはすべて、複製コピーやイレイジャーコーディングフラグメントを含むオブジェクトデータ専用に使用されます。

複製されたコピーのスペース使用を均等にするため、特定のオブジェクトのオブジェクトデータは、利用可能なストレージ容量に基づいて、1つのオブジェクトストアに格納されます。オブジェクトストアが容量いっぱいになると、残りのオブジェクトストアはストレージノードに空き容量がなくなるまでオブジェクトの保存を続けます。

--
メタデータ保護:: StorageGRID は、オブジェクトのメタデータを Cassandra データベースに保存し、LDR サービスと連携します。
+
--
冗長性を確保し、データ損失を防ぐため、各サイトにはオブジェクトメタデータのコピーが3つ保管されています。このレプリケーションは設定変更不可であり、自動的に実行されます。詳細については、link:../admin/managing-object-metadata-storage.html["オブジェクトメタデータストレージの管理"]を参照してください。

--
