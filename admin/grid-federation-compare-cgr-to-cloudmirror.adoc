= StorageGRIDにおけるグリッド間複製とCloudMirror複製の比較
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
グリッドフェデレーションの使用を開始するにあたり、link:grid-federation-what-is-cross-grid-replication.html["グリッド間複製"]とlink:../tenant/understanding-cloudmirror-replication-service.html["StorageGRID CloudMirror レプリケーションサービス"]の類似点と相違点を確認してください。


NOTE: クロスグリッドレプリケーションによって複製されたバケットで CloudMirror を使用することはできません。その逆も同様です。

[cols="1a,3a,3a"]
|===
|  | クロスグリッド複製 | CloudMirrorレプリケーションサービス 


 a| 
主な目的は何ですか？
 a| 
1つのStorageGRIDシステムは、ディザスタリカバリシステムとして機能します。バケット内のオブジェクトは、グリッド間で一方向または双方向にレプリケートできます。
 a| 
テナントが StorageGRID のバケット（ソース）から外部の S3 バケット（宛先）にオブジェクトを自動的にレプリケートできるようにします。

CloudMirrorレプリケーションは、独立した S3 インフラストラクチャ内にオブジェクトの独立したコピーを作成します。この独立したコピーはバックアップとしては使用されませんが、多くの場合、クラウド上でさらに処理されます。



 a| 
どのように設定されているのですか？
 a| 
. 2つのグリッド間でグリッドフェデレーション接続を設定します。
. 新しいテナントアカウントを追加すると、自動的に他のグリッドにも複製されます。
. 新しいテナントグループとユーザーを追加すると、それらも複製されます。
. 各グリッドに対応するバケットを作成し、グリッド間のレプリケーションを片方向または両方向で有効にします。

 a| 
. テナントユーザーは、Tenant Manager または S3 API を使用して CloudMirror エンドポイント（IP アドレス、認証情報など）を定義することで、CloudMirror レプリケーションを設定します。
. そのテナントアカウントが所有するバケットは、CloudMirror エンドポイントを指すように設定できます。




 a| 
誰が設定を担当するのですか？
 a| 
* グリッド管理者は、接続とテナントを設定します。
* テナントのユーザーは、グループ、ユーザー、キー、およびバケットを設定します。

 a| 
通常は、テナントユーザーです。



 a| 
宛先は何ですか？
 a| 
グリッドフェデレーション接続における、もう一方の StorageGRID システム上の対応する同一の S3 バケット。
 a| 
* 互換性のあるS3インフラストラクチャ（Amazon S3を含む）。
* Google Cloud Platform（GCP）




 a| 
オブジェクトのバージョン管理は必要ですか？
 a| 
はい、ソースバケットと宛先バケットの両方でオブジェクトバージョニングが有効になっている必要があります。
 a| 
いいえ、CloudMirrorレプリケーションは、ソースと宛先の両方において、バージョン管理されていないバケットとバージョン管理されたバケットの任意の組み合わせをサポートします。



 a| 
オブジェクトが移動先に移動される原因は何ですか？
 a| 
クロスグリッドレプリケーションが有効になっているバケットにオブジェクトを追加すると、オブジェクトは自動的に複製されます。
 a| 
オブジェクトは、CloudMirror エンドポイントで設定されたバケットに追加されると、自動的にレプリケートされます。CloudMirror エンドポイントでバケットが設定される前にソースバケットに存在していたオブジェクトは、変更されない限りレプリケートされません。



 a| 
オブジェクトはどのように複製されるのか？
 a| 
クロスグリッドレプリケーションはバージョン管理されたオブジェクトを作成し、ソースバケットから宛先バケットにバージョンIDを複製します。これにより、両方のグリッド間でバージョン順序を維持することができます。
 a| 
CloudMirrorレプリケーションにはバージョン管理が有効になっているバケットは必要ないため、CloudMirrorはサイト内のキーの順序のみを維持できます。異なるサイトにあるオブジェクトへのリクエストに対して、順序が維持される保証はありません。



 a| 
オブジェクトを複製できない場合はどうすればよいでしょうか？
 a| 
オブジェクトは、メタデータの保存制限に従って、レプリケーションのためにキューに追加されます。
 a| 
オブジェクトはレプリケーションのためにキューに入れられますが、プラットフォームサービスの制限が適用されます（link:manage-platform-services-for-tenants.html["プラットフォームサービスの利用に関する推奨事項"]を参照）。



 a| 
オブジェクトのシステムメタデータは複製されていますか？
 a| 
はい、オブジェクトが別のグリッドに複製されると、そのシステムメタデータも複製されます。メタデータは両方のグリッドで同一になります。
 a| 
いいえ、オブジェクトが外部バケットに複製されると、そのシステムメタデータが更新されます。メタデータは、取り込みのタイミングや独立した S3 インフラストラクチャの動作によって、場所ごとに異なります。



 a| 
オブジェクトはどのように取得されますか？
 a| 
アプリケーションは、いずれかのグリッド上のバケットにリクエストを送信することで、オブジェクトを取得または読み取ることができます。
 a| 
アプリケーションは、StorageGRID またはS3宛先にリクエストを送信することで、オブジェクトを取得または読み取ることができます。たとえば、CloudMirror レプリケーションを使用してオブジェクトをパートナー組織にミラーリングするとします。パートナーは、独自のアプリケーションを使用して、S3宛先からオブジェクトを直接読み取ったり更新したりできます。StorageGRID の使用は必須ではありません。



 a| 
オブジェクトが削除された場合、どうなりますか？
 a| 
* バージョンIDを含む削除リクエストは、宛先グリッドには複製されません。
* バージョンIDを含まない削除リクエストは、ソースバケットに削除マーカーを追加します。このマーカーは、必要に応じて宛先グリッドにレプリケートできます。
* クロスグリッドレプリケーションが一方向のみに設定されている場合、宛先バケット内のオブジェクトはソースに影響を与えることなく削除できます。

 a| 
結果は、ソースバケットと宛先バケットのバージョン管理状態によって異なります（両者が同じである必要はありません）：

* 両方のバケットがバージョン管理されている場合、削除リクエストを実行すると、両方の場所に削除マーカーが追加されます。
* ソースバケットのみがバージョン管理されている場合、削除リクエストを実行すると、ソースには削除マーカーが追加されますが、宛先には追加されません。
* どちらのバケットもバージョン管理されていない場合、削除リクエストはソースからはオブジェクトを削除しますが、宛先からは削除しません。


同様に、宛先バケット内のオブジェクトは、ソースに影響を与えることなく削除できます。

|===
